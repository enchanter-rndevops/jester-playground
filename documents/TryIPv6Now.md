# AWSでIPv6中心の構成を試してみた

IPv4では以下のような問題がああります。

- IPアドレス枯渇問題
- わかりづらいCIDR設定
- サブネット内でのIPドレス個数制限
- NAT Gatewayによる課金
- NAT由来のネットワークの複雑化

IPアドレス枯渇問題はVPC内ではあまり関係ないかもしれませんが、グローバルIPの割り当てに課金される？されない？を考えたりするのもどうかなと思います。
IPv6を使うことで、これらの問題を解決。これだけでうまくいくなら、みんなIPv6使うよね。

現実はそううまくはいかず、IPv6にしたらしたで、新たな問題が発生するわけです。

- 長いIPv6アドレス
- IP4からのアクセス
- IPv6に対応していない外部サービスへのアクセス

長いIPv6アドレスについては、慣れましょう。そのそもIPアドレスをそのまま使うこともないと思います。
IPv4からのアクセスは、アクセスされる境界部分(ALBなど)だけをデュアルスタックにすることでアクセス可能になります。
IPv6に対応していない外部サービスは、NAT64を使用することができます。
どちらもIPv4がなくなるまでの一時的なものです（その一時的がいつまで続くかという問題もあります）。

```
ECS(Fargate)
      |
      | IPv6
      v
DNS64
      |
      v
NAT64
      |
      | IPv4
      v
IPv4ONLY.example.com
```

デメリットがあるとはいえ、NATが存在しないことでシンプルな構成になる。わかりやすいCIDR, IPアドレス個数制限などのメリットが大きいとも思います。

実際にIPv6環境を作成し、それを試してみようというものです。

## 構成

- **サブネット1** [VPCとインターネットとの境界となるサブネット]
  - AZ1c, AZ1d
  - IGWへのルートあり
  - デュアルスタック

- **サブネット2** [インターネットへのアクセス可能。インターネットからのアクセス不可のサブネット]
  - AZ1c, AZ1d
  - Egress-Only IGW(以降、EIGW)へのルートあり
  - IPv6のみ

- **サブネット3** [VPC内からのみアクセス可能なサブネット]
  - AZ1c, AZ1d
  - IGW, EIGWへのルートなし
  - IPv6のみ

- **サブネット4** [VPC内からのみアクセス可能なサブネット。RDS用]
  - AZ1c, AZ1d
  - IGW, EIGWへのルートなし
  - デュアルスタック

サブネット3を使用する場合、使用するAWSマネージドサービスによりVPCエンドポイントを作成します。
サブネット2を使用する場合、VPCエンドポイントを作成する必要はありません。EIGWのルートからAWSマネージドサービスへアクセスることができます。インターネット上へ出てしまいますが、それが問題ない場合はこれを利用することができます。
たいていの場合はサブネット2でもだと思いますが、実際には、規模やセキュリティ要件により、サブネット2,3を使用するかを判断する必要があるでしょう。
サブネット2を使用し、インターネットに出したくないAWSマネージドサービスのみVPSエンドポイントを作成するといった構成も考えられます。

今回は試験環境なので、サブネット3は使用しません。

> サブネット2をIPv4で実現しようとすると、NAT Gatewayを作り、ルートテーブルを設定するか。グローバルIPアドレスを割り振る（セキュリティグループでインバウンドを許可しない）といった方法となる。IPv6ならEIGRだけで済む。VPCエンドポイントも不要。

構成

```
Internet
  ↓
CloudFront
  + S3 (Frontend)
  + ALB(サブネット1)
    + ECS Fargate(サブネット2)
      + RDS MySQL(サブネット2)
```

## 作成する

- VPCの設定

VPCにIPv6 CIDRが存在しない場合、Amazon提供のIPv6CIDRを追加します。
ルートテーブルdefaultはそのまま使用する。新しく作成してもいいでしょう。
EIGW を作成し、EIGWへのルートテーブルを作成します。

- サブネットの作成

サブネット1,2をAZ1c, AZ1dに作成します。
サブネット1には、IPv4, IPv6両方のCIDRを設定します。
サブネット2にはIPv6のCIDRのみ設定します(このサブネットを使うリソースはIPv4を割り当てないため、IPv4のみのホストに接続ですることができません。必要ならDNS64, NAT64を使用すること)。

VPCには /56 のCIDRが割り当てられています。作成するサブネットは、/64 を割り当てます。
サブネットは /64固定で、IPアドレスの数は十分すぎるほどあるので、IPv4のようにIPアドレス不足を考えたり、重複するCIDRを考慮する必要はありません。

AWSがVPCに割り当てたCIDRが 2406:da14:1959:3200::/56 であれば、

サブネット1AZ1c: 2406:da14:1959:3200::/64
サブネット1AZ1d: 2406:da14:1959:3201::/64
サブネット2AZ1c: 2406:da14:1959:3202::/64
サブネット2AZ1d: 2406:da14:1959:3203::/64

を割り当てます。ここでは単純な連番にしていますが、用途ごとに10の位を分けるなどの工夫もをするのもいいと思います。

```
2406:da14:1959:3200::/56
                 -- ここの部分が割り当て可能なCIDRブロック。256個利用可能
2406:da14:1959:3201::/64
                   -- この部分がCIDRブロック内で利用可能なIPアドレス。18446744073709551616個利用可能
ffff:ffff
--------- 参考。世界中のIPv4で利用可能なアドレスの範囲。
```

サブネットを作成したら、ルートテーブルの割り当てを変更する。
パブリックのほうは、デフォルトのままでも可。

> IPv4ではCIDRブロックを/20にするか、/24にするか考えたり、CIDRブロック長の違いによる重複を考えたり、10進数を16進数にしたりする必要があります。IPv6では何も考えずに 256個あるうちから一つ選んで /64とするだけです。

これらのサブネットを使ってリソースを作成します。

### 0. SSM踏み台用EC2インスタンス

**配置場所**: サブネット1
**方針**: インターネットにHTPSでアクセス可能なサブネット

SSMポートフォワードはIPv4が必要なので、デュアルスタックのサブネットにすること。
RDS用のサブネットを使用し、VPCエンドポイントを作成してもよい。

DEV, STG環境のRDSに接続するのに、SSMポートフォワード用のEC2インスタンスが必要です。
デフォルトでSSMセッションマネージャーが動作しているため、このインスタンスは起動するだけです（デフォルトでセッションマネージャが起動するインスタンスタイプを使用する）。
SSMポートフォワードを使用するためのポリシー設定が必要です。

AWSの機能更新により、このようなEC2インスタンスを作成する必要もなくなるといいですね。

以下のAWSマネージドポリシーを持つロールを作成し、このインスタンスにつける。

```
AmazonRDSDataFullAccess
AmazonSSMManagedInstanceCore
CloudWatchAgentServerPolicy
```

セキュリティグループを作成します。インバウンドの許可はなし。アウトバウンドは0/0に設定すること。
この設定では、セキュリティグループの意味がないように見えますが、このセキュリティグループは、他のセキュリティグループからのインバウンド許可に使用します。

踏み台なのでSSHが必要な気がしますが、SSMだけで問題ありません。キーペアの作成も不要です(コンソールではキーペアなしでは警告が出ますが、する)。SSHをあけることによるリスクのほうが大きいと思います。
何らかの原因でSSMができなくなったら、SSHで接続し、復旧するよりもEC2インスタンスを作成しなおしたほうが速いでしょう。

### 1. RDS MySQLの作成

> RDSは、サブネット3(IGW, EIGWのルートがないサブネット)の使用を検討する。
> 今回は試験環境であり、EIGWのルートの有無は実質的には変わらないので、サブネット2を使用する。

- **配置場所**: サブネット4（RDS用デュアルスタックサブネット）
- **方針**: 外部からの直接アクセスを完全に遮断し、VPC内（ECSやLambda）からの通信のみを許可。

1. **RDSサブネットグループの作成:** VPC Console.
1. VPCコンソールの **「サブネットグループ (Subnet groups)」** から **「DBサブネットグループの作成」** をクリックします。
1. 対象のVPCを選択し、AZ（1c, 1d）に配置されたサブネット4(RDS用サブネット)のサブネットIDを選択して作成します。
   _Verification:_ サブネットグループの詳細画面に、意図したサブネット2のプレフィックス（`/64`）が登録されていることを確認します。

1. **MySQLデータベースの作成:** RDS Console.
1. RDSコンソールの **「データベースの作成」** を選択します。
1. エンジンに **MySQL** を選択し、バージョン（例: 8.0など）を指定します。
1. 接続設定で以下を指定します：

- **VPC**: 対象のVPCを選択
- **DBサブネットグループ**: 先ほど作成したサブネットグループを選択
- **パブリックアクセス**: 「なし (No)」 （※完全なIPv6-onlyプライベート配置）
- **VPCセキュリティグループ**: ECSやLambdaからの接続（ポート3306）を許可するセキュリティグループを選択
  _Verification:_ インスタンスのステータスが「利用可能 (Available)」になり、パブリックアクセスの項目が「いいえ」になっていることを確認します。

> セキュリティグループをここで作成。この段階では、セキュリティグループのインバウンド、アウトバウンドを設定する必要はありません。
> セキュリティグループの設定は、IPアドレスではなく、他のセキュリティグループをもとに許可設定を行います。
> この段階では、他のセキュリティグループは存在しないため、インバウンド、アウトバウンドの設定を行うことができません。すべてのリソースの作成後にセキュリティグループの許可設定を行います。
> 以下のリソース作成時のセキュリティグループもすべて同様です。
> ここで同時に作成せずに、defaultで作成しておき、あとでセキュリティグループをまとめて作成してもいいでしょう。
> アウトバウンドの設定は書いてありません。アウトバウンドの設定はすべて許可を設定します。

> MySQLの場合は、ユーザーごとに接続可能なIPアドレスの設定がある。通常は"%"だけなので、問題ないはず。
> MySQLのユーザーでIPアドレスを指定する意味はあまりないので、すべてのユーザーを"%"にしてしまってもよいでしょう。
> セキュリティグループでもユーザーでIPアドレスを制限するのと同じことができます。厳密にいえば、MySQLのユーザーごとに制限することができませんが、そこまでやる必要はないでしょう。

### 2. ALB (Application Load Balancer) の作成

- **配置場所**: サブネット1（IGWへのルートを持つデュアルスタックサブネット）
- **方針**: インターネットからのトラフィック（IPv4/IPv6両対応）を受け付け、バックエンドのECS等へ転送します。

1. **ターゲットグループの作成:** EC2 Console.
1. EC2コンソールの左メニュー **「ターゲットグループ」** から **「ターゲットグループの作成」** をクリックします。
1. ターゲットタイプに **「IPアドレス」** または **「インスタンス」** を選択し、プロトコル（HTTP/HTTPS）とポートを設定します。
1. VPCに作成したVPCを選択し、ターゲットグループを作成します。
   _Verification:_ ターゲットグループが正常に作成され、ヘルスチェックの設定が完了していることを確認します。

1. **ALBの作成:** EC2 Console.
1. **「ロードバランサー」** から **「ロードバランサーの作成」** ＞ **「Application Load Balancer」** を選択します。
1. 設定項目を入力します：

- **スキップ**: インターネット向け (Internet-facing)
- **IPアドレスタイプ**: **デュアルスタック (dualstack)** （IPv4/IPv6両対応）
- **ネットワークマッピング**: 対象VPCを選択し、サブネット1（AZ1c, AZ1dのIGWルート側）にチェックを入れます。
- **セキュリティグループ**: HTTP/HTTPS（80/443番）のインバウンドを許可するセキュリティグループを選択

3. リスナーとルーティングに、先ほど作成したターゲットグループを紐付けて作成します。
   _Verification:_ ロードバランサーのDNS名に対して、デュアルスタックで名前解決ができ、アクセスできることを確認します。

---

### 3. ECS (Amazon ECS on Fargate) の作成

- **配置場所**: サブネット2（EIGWへのルートを持つIPv6-onlyサブネット）
- **方針**: 外部からの直接露出を避け、ALBからのトラフィックを受け取るバックエンドアプリケーションとして稼働させます。

1. **ECSクラスターの作成:** ECS Console.
1. ECSコンソールの **「クラスター」** から **「クラスターの作成」** をクリックします。
1. クラスター名を入力し、インフラストラクチャとして **「AWS Fargate」** を選択して作成します。
   _Verification:_ クラスターのステータスが「アクティブ (Active)」になることを確認します。

1. **タスク定義とサービスの作成:** ECS Console.
1. **「タスク定義」** から新しいタスク定義を作成します（Fargate起動タイプ、CPU/メモリを指定）。
1. コンテナイメージのURIを指定し、必要な環境変数（データベース接続先など）を設定します。
1. クラスター画面に戻り、**「サービス」** の **「作成」** を選択します：

- **起動タイプ**: Fargate
- **ネットワーク設定**: 対象VPCを選択し、サブネット2（EIGWルート）を指定します。
- **セキュリティグループ**: ALBからの通信を許可するセキュリティグループを設定。
- **パブリックIP**: **オフ (Disabled)** （IPv6-onlyのプライベート環境のため不要）
- **ロードバランシング**: 先ほど作成したALBのターゲットグループをアタッチします。
  _Verification:_ ECSサービスのタスクが「実行中 (RUNNING)」になり、ALB経由で正常に応答することを確認します。

---

### 4. Lambda (VPC内) の作成

- **配置場所**: サブネット2（EIGWへのルートを持つIPv6-onlyサブネット）
- **方針**: VPC内のリソース（RDSなど）にアクセスする必要があるLambda関数を配置します。

1. **Lambda関数の作成とVPC接続設定:** Lambda Console.
1. Lambdaコンソールの **「関数の作成」** から「一から作成」を選択します。
1. ランタイム（Node.js, Pythonなど）を選択し、関数を作成します。
1. 作成後、**「設定 (Configuration)」** ＞ **「VPC」** メニューから **「編集」** をクリックします：

- **VPC**: 対象VPCを選択
- **サブネット**: サブネット2（EIGWルート）を選択
- **セキュリティグループ**: 必要な通信を許可するセキュリティグループを選択

4. 保存します（※VPC内LambdaにはENIがアタッチされます）。
   _Verification:_ Lambda関数の設定画面でVPC、サブネット、セキュリティグループが正しく紐付いていることを確認します。

> **補足（Lambda(VPC外)について）**:
> VPC外（AWSデフォルトのマネージド環境）にLambdaを配置する場合、この構成においては直接インターネット側からインバウンド通信を受け付けることができないため、**ALBを経由したルートからのみアクセスが可能**となります。
> Lambdaについては最新のIPv6対応状況を確認すること。リージョンにより対応状況が異なるようです。

### 5. API Gateway の作成

- **配置場所**: サブネット1（IGWへのルートを持つデュアルスタックサブネット / またはリージョナル/HTTP API）
- **方針**: クライアントからのAPIリクエストを受け付け、バックエンドのLambdaやECSへルーティングします。

1. **API Gatewayの作成と統合:** API Gateway Console.
1. API Gatewayコンソールから **「APIの作成」** を選択します（HTTP APIまたはREST API）。
1. ルート（リソースとメソッド、例: `GET /items`）を追加します。
1. 統合先として、バックエンドの **Lambda関数** または **ALB（HTTP/HTTPSエンドポイント）** を指定します。
1. APIをデプロイし、ステージ（例: `default` や `prod`）を作成します。
   _Verification:_ 発行されたAPIのInvoke URLに対してリクエストを送り、バックエンドから正しいレスポンスが返ってくることを確認します。

> **補足:API Gatewayの必要性について**
> 個人的にはALBで十分なケースが多い。
> ALBは余計な機能が多く、設定がやりにくい。レスポンスの形式をAPI Gatewayか返すものと、Lambaで返すものとでそろえずらいといった問題があるように思う。
> API Gateawyなし。ALBなしでも、自前の軽量フロントをサブネット1に置けばいいだけ（そもそもALBなしの構成というのもあまりないと思う）。
> ALBとLambdaを組み合わせる場合、ALBのターゲットが増えるという問題があるが、これは ALB->自前軽量フロント->Lambdaで解決。
> 軽量フロントなら、Lambaでちょっとしたスクリプトを書けばいいだけ（パスからLambdaを振り分けるような感じ）。認証、認可が必要なら、Backendと同じことをするものを作成するか、Backendに統合する。
> API Gatewayで本当に必要になるのはUsage Planくらい？
> API GatewayではAPI key を使うことができるけど、これは認証の代わりになるものではない。API keyを使うくらいなら、API keyを使用せずに、認証、認可を使うことを検討することを推奨。
> API keyなら軽量ゲートウエイでも簡単に実装できてしまうので、API keyが必要だからAPI Gatewayを使うという理由にはならないのでは?

### 6. セキュリティグループの設定

それぞれのリソースに設定したセキュリティグループのインバウンドを設定する。
IPアドレスではなく、作成済みのセキュリティグループで許可設定を行うこと。
ポート番号は実際に通信するポートにすること。

- RDS用セキュリティグループのインバウンド許可
  - SSM踏み台用セキュリティグループ 3306
  - ECS用セキュリティグループ 3306
  - Lambda用セキュリティグループ 3306

- ECS用セキュリティグループのインバウンド許可
  - ALB用セキュリティグループのインバウンド 80

その他構成に合わせて必要なインバウンド許可を行うこと。

### さいごに

IPv6のみの環境を作成するつもりでしたが、実際にやってみると意外と IPv4 が必要なところが多いと感じました。
特に SSM 用の踏み台や RDS 周辺は、現時点では完全な IPv6-only にすることができず、デュアルスタックのサブネットが必要になります。
RDSのほうは、デュアルスタックサブネットを使うだけですが、SSMのほうはIPv6のみならEIGWのみでできるのに、IPv4が必要なせいて複雑なことになっている印象があります。

CIDR 設計をほとんど考えなくてよいことと、NAT Gateway が不要になることのメリットが非常に大きいと感じました。

IPv4 が完全になくなる日はまだ先でしょう。しかし、AWS の主要サービスはすでに IPv6 に十分対応しており、少なくとも新規構築の検証環境であれば IPv6 を第一候補として考えてもよい段階に来ているのではないかと思います。
