# AWSの通信経路をVPC起点で整理してみた

AWSのネットワークを理解するのに、まずはこれらを区別するようにしましょう。

1. VPC(EC2, RDS, Lambda(VPC))
2. AWSマネージドサービス(S3, シークレットマネージャー, パラメータストアなど)
3. インターネット

## 1. VPC → 別VPC（AWS内）

- **ベストな方法:** **VPCピアリング (VPC Peering)** または **AWS Transit Gateway (TGW)**
- **特徴:**
- **VPCピアリング:** 1対1のシンプルな接続。同一リージョン内であればデータ転送量も安価で、ルートテーブルの設定だけで直結できるため最も手軽。
- **Transit Gateway:** 3つ以上のVPCやオンプレミス環境をハブ＆スポーク型で一元管理する場合に最適。
- 社内サービスがインターネットからアクセスできる場合、設定の手間を省ける VPC → インターネット も検討。

## 2. VPC → 社内サービス（オンプレミス・データセンター等）

- **ベストな方法:** **AWS Site-to-Site VPN** または **AWS Direct Connect**
- **特徴:**
- **Site-to-Site VPN:** インターネット経由でIPsecトンネルを構築し、暗号化された安全な通信を行う。コストを抑えて社内ネットワークとAWSを繋ぎたい場合の主流。
- **Direct Connect:** 専用線を引くことで、インターネットを一切経由しない高速かつ安定した閉域網接続を実現する（大規模・ミッションクリティカル向け）。
- ※個人の開発者やリモートワーカーから直接VPC内へつなぐ場合は **AWS Client VPN** も選択肢になります。

## 3. VPC → インターネット上のサービス（外部SaaS・外部API等）

- **ベストな方法:** **NAT Gateway**
- **特徴:**
- プライベートサブネットからインターネット上の外部サービス（AWS外）へ安全にアウトバウンド通信を行うための標準的なマネージドGW。

- **方法:IPv6**
- **特徴:**
- NAT Gateway不要。IPv4グローバルアクセスを付与したのと同じ感覚で使える。
- 接続先にIPv6がないと接続することができない。
- IPv6の設定が必要なので、設定が煩雑。

## 4. VPC → AWSサービス（マネージドサービス）

- **ベストな方法:** **VPCエンドポイント (Interface型 / Gateway型)**
- **特徴:**
- S3、DynamoDB、SQS、Secrets Manager、SSMなどのAWSマネージドサービスにアクセスする場合、インターネットやNAT Gatewayを一切経由せず、**AWSの内部ネットワーク網（クラウド内）で安全かつ高速に完結**させる方法。
- セキュリティとコスト（NATのデータ処理課金回避）の両面において最も推奨されるベストプラクティス。

## 5. Lambda(VPC外)

インターネット上から呼び出す場合と同じ。
VPC内にあるものにはアクセスできない。
AWS マネージドサービスは、そのまま呼び出すことができる。
インタネット上にあるものは直接呼び出すことができる。

セキュリティ上の問題（経路がインターネットになる）。
VPC内のリソースが使えない（RDSにアクセスできない）。
といった問題があるので、LambdaはVPC内で実行することを推奨。
VPC内で実行した場合は、EC2インスタンスと扱いは同じ。

## Lambdaの呼び出し

API Gatewayは、独自のルーティングや複雑な設定の割に管理しづらく、軽量なバックエンド構成（Spring Bootなど）を使用している場合にはオーバースペックになりがち。

Lambdaを起動するための代替アプローチとしては、以下のような選択肢が考えられます。

1. **ALB + Lambda 統合**

- ALB（Application Load Balancer）のターゲットグループにLambdaを指定する構成です。
- **メリット:** すでにALBをフロントに置くアーキテクチャであれば、API Gatewayを通さずにALBのルーティング規則（パスベース等）で直接Lambdaを呼び出せます。HTTPSや独自ドメインのルーティングもALB側で一元管理できます。

2. **ECS（Spring Boot）から直接非同期・同期呼び出し（AWS SDK）**

- バックエンドのECSから、イベントや処理に応じてAWS SDKでLambdaを直接起動する（あるいはSQSを挟んでトリガーする）構成です。
- **メリット:** APIのエンドポイントとして外に露出させる必要がない内部処理やバッチ、非同期処理であれば、API GatewayやALBを介さずに最もシンプルに連携できます。

API Gatewayの代わりにALBを入り口に使う形や、バックエンドからの直接呼び出しなど、どのような用途（Webのフロントから直接叩くのか、バックエンドの非同期処理として使うのか）でLambdaを動かしたいかによって選択が変わってきます。

ALBから呼ぶ。またはECSから直接実行する場合、起動時間がかかるJavaは不向き。
SQSからLambdaを呼ぶ場合には、多少起動時間がかかっても、非同期処理であるため問題ない。

ECSからLambdaを起動するメリットはあまりないように感じられるが

- ECSのコンピューティングリソースをおさえるため、Lambda側で処理する。
- 複数のスレッドを実行する場合、Lambdaでスケーリングする

といったケースも考えられる。こういうことはあまりないような気がするけど、一応覚えておくのもいい。

Springの非同期処理機能を使うのであれば、SQSをつかわないという選択肢もありえる。
SQSを使うと、AWSの構成が複雑になるし、Lambda側の処理もめんどくさいことになるので、まずはSQSなしで考えてみよう。
処理自体は、あとでSQS用のラッパーを書くだけなので、移行はそんなに難しくない。
メッセージが最大10件（設定可能）送られてくるので、失敗したものだけが再送信されるようにするという点に注意。
これがないと、1件失敗しても、10件再送信されてしまう。
